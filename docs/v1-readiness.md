# Open Core v1 acceptance evidence

This is an implementation checklist for the supplied Open Core specification, not a declaration that a production release has been published. Local evidence is generated by the commands below; remote CI and registry publication remain separate verifications.

| Requirement group                                         | Implementation and evidence                                                                                                                                            |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Product/commercial boundaries (§1–3, §30, §54–56, §62–63) | Canonical public packages and injected infrastructure; isolated private consumer test. No accounts, billing, hosted jobs, checkout, payments or network intelligence.  |
| License/contribution/dependency policy (§4–6)             | Official Apache license, per-package notices, trademark policy, DCO, transitive license audit and failure-case tests.                                                  |
| Workspace/package boundaries (§7–8, §42–43)               | Strict TypeScript, Node 24, pnpm/Turbo, explicit exports, package tarball and blocked-internal-import checks.                                                          |
| Canonical data/normalization (§9–10)                      | Zod/JSON Schema/types, deterministic identities, decimal prices, variants, unknown states, provenance and compatibility policy.                                        |
| Detection/connectors/security/scanning (§11–15)           | Platform detection, generic web and WooCommerce, registered connector detection, bounded safe HTTP, DNS pinning, robots, structured progress/events and fixture scans. |
| Validation/scoring/query (§16–18)                         | Stable deterministic rule IDs, versioned configurable weights and shared query engine; unit/property cases and branch coverage.                                        |
| REST/MCP (§19–20, §25)                                    | OpenAPI inputs/responses, domain errors, official MCP SDK and client compatibility, actual CLI serve test and shared catalog replacement.                              |
| ACP/UCP/registry/CLI (§21–24)                             | Pinned official schemas, verified catalogs, exact metadata in `protocols`, JSON/ACP/UCP export commands and explicit unsupported capabilities.                         |
| Web demo (§26)                                            | URL scan, offline demo, score/categories/products/issues, protocol downloads, same-origin loopback service and Chromium acceptance.                                    |
| Storage/extension/logging (§27–29, §45–46)                | Memory/SQLite ports, injected clock/logger/events/credentials, domain errors and no runtime remote telemetry.                                                          |
| Contracts/properties/security/integration (§31–37, §51)   | Reusable connector suite, complete external example, platform-specific pagination/duplicates/variants, malformed inputs and crawl→export→REST/MCP acceptance.          |
| Coverage/CI/supply chain/releases (§38–41)                | Per-package coverage floors, OS matrix, audits, CodeQL, immutable Action revisions, tarball verification, CycloneDX SBOM and manual provenance publishing workflow.    |
| Performance (§44)                                         | 100 / 10,000 / 100,000-product normalization, validation, search and serialization benchmark with memory reports.                                                      |
| Documentation/developer experience (§47–50)               | `pnpm dev`, no-key offline demo, extension guides, release instructions, architecture docs and six ADRs.                                                               |
| Scope and execution discipline (§52–53, §57–60)           | Laptop-local monorepo, no mandatory AI providers or distributed services, PLAN.md and baseline quality gates.                                                          |
| Final functional scenario (§61)                           | Offline end-to-end acceptance, CLI exports and actual CLI serving through REST and official MCP client. Public `npx` usage requires the release described below.       |

## Commands and artifacts

Baseline: `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm licenses:check`, `pnpm security:check`, `pnpm build`.

Additional required checks: `pnpm test:coverage`, `pnpm test:e2e`, `pnpm packages:check`, `pnpm benchmark`, `pnpm sbom:generate`.

Artifacts: `reports/coverage/`, `reports/packages/`, `reports/licenses.json`, `reports/sbom.json`, `reports/benchmarks.json`, `reports/web-demo.png`. CI uploads these rather than committing generated artifacts.

## External release prerequisites

- Verify the current commit in GitHub's Linux/macOS/Windows matrix and CodeQL. The previous Windows failure is not proven fixed by a local Linux run. LF attributes and untouched schema snapshots remove a cross-platform checksum hazard; inspect the actual new job logs.
- Establish npm name/scope ownership and trusted publishing for the packages, configure the `npm-release` environment, choose/review the release version, and authorize publication. No package publication, npm ownership claim or v1 tag is implied by the code changes.
- Confirm the security-reporting channel and trademark ownership with the maintainers before public release.
- After publication, perform a clean-machine `npx agentshelf` installation and the documented scan/export/serve scenario. Live-store extraction varies with the merchant's public surfaces and robots policies; CI uses deterministic fixtures.

These are release operations and independent evidence, not implemented Cloud features. See [releasing.md](releasing.md) for the exact procedure.
